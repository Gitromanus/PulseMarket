# 04. Прокси LTESpace

Интеграция с [LTESpace](https://ltespace.com) — мобильные LTE/4G‑прокси с
ротацией IP. Публичный API: `https://api.ltespace.com`, спецификация —
`https://api.ltespace.com/openapi.json` (её же рендерит кабинет `#/api-docs`).

## Что уже сделано

| Файл | Назначение |
| --- | --- |
| `backend/app/integrations/ltespace.py` | клиент API, сборка строк прокси, синхронизация файла пула, смена IP |
| `backend/app/api/ltespace.py` | локальные методы `GET /api/ltespace/status`, `POST /api/ltespace/sync`, `POST /api/ltespace/rotate` |
| `backend/app/core/config.py` | блок настроек `ltespace` в `settings.json` |
| `backend/app/core/supervisor.py` | синхронизация прокси перед прогоном, смена IP при блоке Ozon |
| `backend/app/api/settings.py` | проверка ключа и баланса при сохранении настроек |
| `ui/src/pages/SettingsPage.tsx` | карточка «Прокси LTESpace (API)» |

## Настройка

1. В кабинете LTESpace: **Настройки → API → Выпустить ключ**. Ключ показывается
   один раз, новый ключ отзывает предыдущий.
2. В приложении: **Настройки → Основные → Прокси LTESpace**:
   - вставить ключ `ltespace_…`;
   - включить «Использовать прокси из аккаунта LTESpace»;
   - выбрать протокол пула (`http` подходит и для HTTPS, `socks5` — SOCKS5);
   - нажать «Сохранить», затем «Проверить ключ» и «Подтянуть прокси».
3. Прокси попадают в отдельный файл
   `%APPDATA%/pf-automation/proxies_ltespace.txt`. При включённой интеграции
   этот файл становится **основным пулом**: `general.proxies_file` указывает на
   него, поэтому потоки, «Список прокси», «Закрепить за профилями» и проверка
   на Ozon работают именно с прокси LTESpace. Профили, привязанные к старым
   (ручным) адресам, автоматически перезакрепляются за новым пулом.

Пароли в файле хранятся как есть (так же, как для ручных прокси), наружу через
локальный API не отдаются — только `host:port` и тариф.

## Поведение

- **Перед прогоном** (если включено «Обновлять список прокси перед прогоном»)
  приложение делает `GET /proxies`, перезаписывает файл и только потом создаёт
  пул. Истёкшие (`active=false`), замороженные (`frozen≠0`) и просроченные
  (`expire_ts` в прошлом) каналы пропускаются.
- **Сохранение настроек** с включённым LTESpace сразу синхронизирует пул:
  проверка прокси, «Список прокси» и закрепление профилей видят только
  выбранные прокси LTE, а не старый ручной файл.
- **При блоке Ozon** (`ozon_blocked`/антибот) и включённой опции «Менять IP при
  блоке» приложение берёт прокси потока, находит его по порту и вызывает ссылку
  ручной ротации (`manual_rotation_url`). Работает на приватном тарифе; на
  `shared` ручной ротации нет — IP меняется только по таймеру, в лог пишется
  предупреждение.
- **При 407** (Chrome не приложил логин/пароль прокси) первый повтор идёт тем же
  прокси — гонка на первом запросе обычно проходит. Если 407 повторился, а
  LTESpace включён, доступы перезапрашиваются через API, пул перезагружается, и
  профиль перезакрепляется за обновлённым адресом.
- **Закрепление профилей** не рвётся: при ротации LTESpace сохраняет порт,
  логин и пароль, меняется только внешний IP. `ProxyAssignments` хранит строку
  `scheme://login:pass@host:port`, поэтому профиль остаётся на том же канале.
- **Чистка Service Worker перед запуском.** Старый SW (например, Ozon)
  перехватывает переходы и отдаёт закэшированный неуспешный ответ — страница
  падает с `ERR_HTTP_RESPONSE_CODE_FAILURE`/407, хотя прокси рабочий. На
  «безакке» (чистый профиль) та же ссылка открывается. `VanillaProvider`
  удаляет `Default/Service Worker` перед каждым запуском: кэш SW не входит в
  отпечаток, личность профиля не страдает.

## Потоки, IP и капча

- **Потоки параллельны.** Каждый поток — отдельная задача `_worker`, задания
  берутся атомарно из SQLite. Поток, у которого нет свободных строк, не
  блокирует остальные: он простаивает и ждёт, пока другой поток вернёт строку в
  очередь (например, при повторе). «Ждём профиль, чей прокси не занят» возникает
  только когда все прокси заняты (`proxy_max_threads` × число прокси меньше
  числа потоков) — добавьте прокси или уменьшите потоки.
- **IP закреплён за профилем.** `ProxyAssignments` хранит пару «профиль →
  прокси», поэтому повторный заход того же профиля идёт с того же IP. Новые
  профили равномерно раскладываются по пулу. IP меняется только когда:
  включён «Новый IP перед каждым прогоном» (все каналы с ручной ротацией),
  включён «Менять IP при блоке», сработала капча с автоперезапуском, или
  сработал таймер ротации на стороне LTESpace.
- **Видно, с какого IP работает поток.** При открытии сессии приложение
  запрашивает внешний IP через прокси браузера (`context.request` →
  `api.ipify.org`) и пишет его в лог и в карточку потока. Адрес прокси
  показывается как `scheme://host:port` без звёзд, учётные данные остаются в
  файле. После ручной ротации в лог пишется `old_ip → new_ip`, поэтому смену
  видно сразу; проверка прокси на Ozon тоже показывает IP каждого канала.
- **Капча-пазл** (слайдер) при включённом «Капча: остановить прогон…» больше не
  ждёт человека 5 минут: поток сразу отдаёт `ozon_captcha`, supervisor закрывает
  браузеры, меняет IP у всех каналов с ручной ротацией, ждёт
  `captcha_restart_delay_sec` и запускает прогон заново. Если ручной ротации нет
  (`shared`), прогон не останавливается навсегда: приложение запоминает реальный
  внешний IP каждого прокси (запрос `api.ipify.org` через сам прокси — поле `ip`
  в API LTESpace статично и смену не показывает), проверяет его каждые 20 секунд
  и, как только сменился хотя бы один канал, продолжает прогон **на нём**, не
  дожидаясь остальных: порты со старым IP исключаются из пула на этот прогон, а
  число потоков ужимается под число свежих прокси. Ожидание ограничено
  20 минутами, после чего в лог пишется ошибка.
  После `captcha_restart_limit` перезапусков подряд автоперезапуск выключается.
  Обычный proof-of-work челлендж по-прежнему проходит сам за 2–10 секунд.

## Используемые методы API

| Метод | Зачем |
| --- | --- |
| `GET /user/balance` | проверка ключа и баланса в настройках |
| `GET /proxies` | список прокси, сроки, ссылки ротации |
| `GET manual_rotation_url` | смена IP приватного тарифа (без ключа, обычный GET) |

Остальные методы спецификации (`/orders/*`, `/channels/available`, `/geo`,
`/prices`, `PATCH /proxies/*`) клиентом пока не используются. Покупка и
продление требуют списания денег, поэтому автоматику для них добавлять только
с явным подтверждением оператора.

## Особенности API, о которых легко забыть

- Бизнес‑ошибки приходят с **HTTP 200** и `status: "error"` — проверять тело,
  а не только код ответа. `422` — невалидное тело запроса.
- Управление прокси — **по порту**, а не по `id`. `id` постоянный, его стоит
  хранить у себя; порт может быть выдан повторно.
- Периоды заказа: 1, 7, 14, 30, 90 дней. Тарифы: `shared`, `sharednowait`,
  `private`, `privatenowait`, `multiport`, `multiregion`.
- Ротация: 0–60 минут; для `shared` допустимы только 2 и 5. `0` — только ручная
  ротация (приватный тариф).
- Для работы с аккаунтами Ozon нужен стабильный IP: приватный тариф с ручной
  ротацией подходит лучше, чем `shared` с таймером.
